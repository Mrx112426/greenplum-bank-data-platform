# Distributed Data Platform

**Авторы:**

- Мазориев У.А.
- Мещеряков Н.М.
- Шадрухин А.С.

Проект представляет собой универсальную распределенную платформу для сбора, хранения, проверки и обработки данных из нескольких источников. Платформа не привязана к конкретной предметной области и может быть адаптирована для работы с транзакционными, справочными, событийными и файловыми данными.

Центральным хранилищем выступает Greenplum. В нем реализуются слои Staging, Core и DM, выполняются преобразования и формируются аналитические витрины. Готовые наборы могут передаваться различным потребителям данных: аналитическим СУБД, вычислительным платформам, приложениям и другим сервисам. Apache Airflow управляет ETL/ELT-конвейером, а проверки Data Quality контролируют полноту, уникальность, целостность и корректность данных.

## Цель проекта

Цель проекта - разработать воспроизводимую распределенную платформу данных, обеспечивающую:

- загрузку данных из реляционных, файловых и внешних источников;
- централизованное хранение и обработку данных в Greenplum;
- разделение хранилища на слои Staging, Core и DM;
- автоматическое выполнение ETL/ELT-процессов;
- контроль качества данных на ключевых этапах;
- распределение данных и параллельную обработку запросов;
- демонстрацию зеркалирования сегментов Greenplum;
- передачу готовых витрин выбранному потребителю данных.

## Архитектура

```text
PostgreSQL / другие БД --------------------+
                                           |
API / внешние системы -> MinIO (S3) -------+--> Greenplum
Файлы CSV / Parquet -> MinIO (S3) ---------+    |-- Staging
                                                |-- Core
                                                `-- DM
                                                     |
                                                     v
                                           Потребитель данных

                 Apache Airflow + Data Quality
```

![Архитектура распределенной платформы данных](docs/images/platform-architecture.png)

На схеме показано, как данные из операционных баз, API и S3-совместимого файлового хранилища поступают в Greenplum, проходят слои Staging, Core и DM, а затем передаются потребителю данных. Apache Airflow оркестрирует процессы, а Data Quality обеспечивает контроль данных на каждом этапе.

Данные из доступных реляционных источников могут загружаться непосредственно в Greenplum. MinIO используется для файлов, выгрузок внешних систем и данных, полученных через API. Такой подход не делает объектное хранилище обязательным промежуточным звеном для каждого источника.

| Компонент | Назначение |

| Apache Airflow | Оркестрация ETL/ELT-процессов |
| Потребитель данных | Получение подготовленных витрин для последующей обработки или анализа |

## Слои хранилища

### Staging

Слой первичной загрузки сохраняет данные в структуре, близкой к источнику. Он используется для технической приемки, повторной обработки и фиксации метаданных загрузки.

### Core

Core содержит очищенные и согласованные данные. Для авиаперевозок хранится текущий полный снимок, для курсов валют сохраняется история по календарным датам. Здесь выполняются контроль бизнес-ключей, проверка допустимых значений и ссылочной целостности. Все строки с повторяющимся ключом отправляются в карантин, чтобы не выбирать произвольную версию записи.

### DM

Слой DM содержит готовые предметные витрины. Они строятся на основе Core и оптимизируются под конкретные сценарии анализа или потребления. После проверки витрины передаются выбранному потребителю данных.

## Data Quality

Проверки качества встроены в ETL/ELT-конвейер и выполняются после загрузки в Staging, перед публикацией в Core, после формирования DM и после передачи данных потребителю.

| Категория | Пример проверки |
|---|---|
| Полнота | Обязательные поля не содержат `NULL` |
| Уникальность | Бизнес-ключи и идентификаторы не дублируются |
| Целостность | Ссылки на связанные сущности корректны |
| Допустимость | Значения входят в разрешенный перечень |
| Диапазон | Числовые показатели находятся в допустимых границах |
| Актуальность | Загружен ожидаемый временной срез |
| Сверка | Количество строк и контрольные суммы совпадают между слоями |
| Распределение | В Greenplum отсутствует критический перекос данных |

Результаты загрузок и проверок сохраняются в технических таблицах:

```text
dq.check_results
dq.rejected_records
dq.pipeline_runs
dq.layer_state
```

Ошибочные строки изолируются в карантине, корректные данные публикуются с предупреждением. Зависимые записи с отсутствующим принятым родителем также отклоняются. Ошибки инфраструктуры, SQL и технической сверки останавливают публикацию слоя. Независимый ежедневный аудит записывает обнаруженные нарушения в таблицу DQ и логи; отсутствие предупреждений соответствует статусу SUCCESS, наличие предупреждений соответствует WARNING в журнале DQ. DAG при успешно выполненном аудите остается зеленым.

## Распределение данных в Greenplum

Greenplum использует MPP-архитектуру и распределяет строки между сегментами. Это позволяет выполнять части аналитического запроса параллельно.

Для крупных таблиц используется распределение по ключу:

```sql
DISTRIBUTED BY (entity_id);
```

Для небольших справочников может применяться размещение копии на каждом сегменте:

```sql
DISTRIBUTED REPLICATED;
```

Ключ распределения выбирается с учетом кардинальности, равномерности значений и частоты использования поля в операциях соединения. В проекте планируется сравнить несколько стратегий и проверить наличие data skew.

## Зеркалирование сегментов

Для демонстрации отказоустойчивости в Greenplum используются primary- и mirror-сегменты. В проекте планируется показать имитацию отказа основного сегмента, переключение на зеркало и восстановление штатной конфигурации.

Зеркалирование повышает доступность кластера, но не заменяет резервное копирование.

## Потребители данных

Потребитель данных не является центральным DWH и не содержит основную бизнес-логику преобразований. Ему передаются уже сформированные и проверенные витрины Greenplum DM.

В качестве потребителя могут использоваться:

- аналитическая СУБД;
- Apache Spark или другая вычислительная платформа;
- прикладной сервис;
- система машинного обучения;
- инструмент исследования данных;
- внешний контур обмена данными.

Перед публикацией выполняются:

1. Проверка успешного формирования витрины в Greenplum.
2. Контроль обязательных полей и уникальности ключей.
3. Очистка или замена целевого среза у потребителя, если это требуется выбранной технологией.
4. Загрузка подготовленных данных.
5. Сверка количества строк и контрольных показателей.

## Оркестрация

Apache Airflow управляет зависимостями, расписанием, повторными запусками и контролем состояния процессов.

Реализованные DAG-процессы:

| DAG | Назначение |
|---|---|
| `platform_healthcheck` | Доступность PostgreSQL, MinIO и Greenplum |
| `edw_pipeline` | Управляющий DAG: Staging, Core, DM, DQ; ежедневно в 03:00 Europe/Moscow |
| `edw_staging` | Полная загрузка PostgreSQL и инкрементальная загрузка ЦБ через MinIO |
| `edw_core` | Проверки, карантин и транзакционная публикация Core |
| `edw_dm` | Построение четырех аналитических витрин |
| `edw_data_quality` | Аудит опубликованных данных после конвейера и отдельно ежедневно в 06:00 Europe/Moscow |

DAG слоев запускаются управляющим DAG последовательно с общим идентификатором пакета. Самостоятельный запуск Core или DM использует последний опубликованный вышестоящий слой. Повтор управляющего запуска переиспользует идентификатор пакета; параллельные запуски одного DAG ограничены. Все задачи публикации и аудит берут общую транзакционную блокировку технического состояния перед работой с таблицами. Это сериализует изменения и исключает пересечение ручного запуска слоя с аудитом или другим слоем.

### 3. ETL и Data Quality

На третьем этапе реализуется движение данных от источников в Greenplum.

ETL-конвейер включает:

1. Полную выгрузку восьми таблиц PostgreSQL из согласованного снимка в Greenplum Staging через COPY.
2. Ежедневное получение курсов ЦБ и сохранение исходных XML-ответов в MinIO.
3. Инкрементальную загрузку курсов из MinIO в Staging с повторной обработкой последних дат.
4. Очистку и перенос данных в Core.
5. Формирование аналитических витрин в DM.

В ETL-процессы добавляются проверки Data Quality:

- наличие обязательных данных;
- отсутствие дублей;
- уникальность ключей;
- корректность типов и диапазонов;
- ссылочная целостность;
- совпадение количества записей между слоями;
- актуальность загруженных данных.

Некорректные записи сохраняются отдельно, а результаты проверок записываются в технические таблицы. Корректная часть набора публикуется с предупреждением. Ошибки соединения, SQL и нарушение технической сверки прерывают загрузку и откатывают транзакцию публикации.

**Результат этапа:** автоматизированный ETL-конвейер с контролем качества данных.

### 4. Репликация в Greenplum

На четвертом этапе настраивается отказоустойчивость Greenplum с помощью зеркальных сегментов.

Для каждого primary-сегмента создается mirror-сегмент, содержащий синхронизированную копию данных.

Проверка включает:

- просмотр состояния primary и mirror;
- контроль синхронизации сегментов;
- имитацию отказа primary-сегмента;
- переключение на mirror-сегмент;
- проверку доступности данных после переключения;
- восстановление и повторную синхронизацию сегмента.

**Результат этапа:** демонстрация сохранения доступности данных при отказе одного из сегментов.

**Контроль выполнения:**

- [ ] развернуть mirror-сегменты Greenplum;
- [ ] проверить синхронизацию primary- и mirror-сегментов;
- [ ] смоделировать отказ primary-сегмента;
- [ ] подтвердить переключение и доступность данных после отказа.

В локальной среде это функциональная демонстрация. В промышленной системе primary и mirror должны размещаться на разных физических серверах.

### 5. Шардирование в Greenplum

На пятом этапе исследуется распределение данных между сегментами Greenplum.

Для таблиц выбираются разные способы распределения:

- `DISTRIBUTED BY` для распределения по бизнес-ключу;
- `DISTRIBUTED RANDOMLY` для равномерной первичной загрузки;

- анализ операций Motion в планах запросов;
- сравнение времени выполнения запросов;
- оценка влияния способа распределения на соединения и агрегации.

**Результат этапа:** обоснованная схема распределения таблиц и демонстрация массово-параллельной обработки данных в Greenplum.

## Практическая ценность

Проект объединяет проектирование DWH, работу с распределенной СУБД, оркестрацию, контроль качества и публикацию витрин внешнему аналитическому потребителю.

Платформа демонстрирует полный инженерный процесс:

```text
источники -> загрузка -> Staging -> Data Quality -> Core -> DM -> потребитель данных
```

Архитектура не зависит от конкретной предметной области. Для адаптации проекта достаточно заменить модели источников, правила преобразования, проверки качества и состав витрин.

## Ограничения демонстрационной реализации

Проект предназначен для локальной демонстрации архитектурных принципов. Количество сегментов и объем данных будут меньше, чем в промышленном кластере.

Для промышленной эксплуатации дополнительно потребуются централизованный мониторинг, резервное копирование, управление секретами, разграничение доступа, шифрование соединений и отдельные узлы кластера.

## Этап 2. Локальная инфраструктура

Для локальной демонстрации развернут Docker-контур, включающий:

- PostgreSQL как тестовый операционный источник;
- отдельный PostgreSQL для метаданных Apache Airflow;
- MinIO как S3-совместимую raw/landing-зону;
- Greenplum как центральное распределенное хранилище данных;
- Apache Airflow с `LocalExecutor`;
- автоматическое создание бакета `raw-data`;
- автоматическое создание базы `dwh` и схем `staging`, `core`, `dm`, `dq`;
- диагностический DAG `platform_healthcheck`.

MinIO хранит исходные файлы и внешние выгрузки, а табличные слои DWH размещаются в Greenplum. Локальный контейнер Greenplum содержит координатор и два primary-сегмента. Mirror-сегменты в текущую конфигурацию не входят: они будут добавлены отдельно на этапе демонстрации репликации.

Для локального стенда используется поддерживаемый community-форк `pgsty/minio`, поскольку распространение официальных community-образов MinIO прекращено. Он сохраняет совместимость с S3 API и привычными параметрами запуска MinIO.

### Требования

- Windows 10 или Windows 11;
- Docker Desktop с включенным Linux containers mode;
- Docker Compose V2;
- не менее 8 ГБ оперативной памяти, выделенной Docker Desktop;
- свободные порты `5433`, `5434`, `8080`, `9000` и `9001`.

При первом запуске скрипт:

1. Создаст `.env` из `.env.example`.
2. Соберет образ Airflow с необходимыми провайдерами.
3. Запустит PostgreSQL, MinIO и Greenplum.
4. Создаст бакет MinIO.
5. Создаст базу `dwh` и схемы Greenplum.
6. Инициализирует базу метаданных и пользователя Airflow.
7. Запустит Airflow Webserver и Scheduler.

## Этап 3. ETL и Data Quality

### Запуск

После запуска инфраструктуры и установки базы `demo`:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-edw.ps1
```

Скрипт включает пять DAG и запускает `edw_pipeline`. Ход выполнения доступен в Airflow. При первом запуске автоматически создаются девять таблиц Staging, девять таблиц Core, четыре витрины DM и служебные таблицы DQ. Для двух больших таблиц и других фактов используется сжатое колоночное хранение Greenplum AOCO. Данные не передаются через XCom: PostgreSQL COPY использует временный файл с ограниченным буфером памяти, а для ЦБ через XCom передаются только пути и контрольные суммы объектов.

По умолчанию первый запуск получает курсы за 30 календарных дней до конечной даты включительно. Последующие запуски загружают новые даты и перечитывают последние семь дней. Параметры `CBR_INITIAL_DAYS`, `CBR_LOOKBACK_DAYS` и `CBR_CHANGE_WARNING_PCT` задаются в `.env`. Удаление и вставка обрабатываемых срезов выполняются в одной транзакции, остальные даты сохраняются.

В форме запуска `edw_pipeline` в Airflow можно указать интервал курсов:

```json
{
  "cbr_start_date": "2026-10-01",
  "cbr_end_date": "2026-10-14"
}
```

Без параметров конечной датой становится день перед концом интервала запуска в часовом поясе Europe/Moscow. Автоматическая историческая очередь Airflow отключена (`catchup=False`). Для начальной загрузки можно задать до 366 календарных дат за один запуск.

Исходные ответы ЦБ сохраняются без перезаписи предыдущих пакетов:

```text
raw/cbr/request_date=YYYY-MM-DD/batch_id=<batch>/response.xml
```

Повтор задачи в том же пакете использует уже сохраненный XML, а новый пакет может получить исправленную версию ответа. Дата запроса (`request_date`) и дата курса из XML (`rate_date`) хранятся отдельно. Номинал учитывается при расчете курса за единицу, денежные значения обрабатываются через Decimal и NUMERIC.

### Витрины

| Витрина | Зерно и назначение |
|---|---|
| `dm.ticket_flight_details` | Одна строка на пару билет, рейс; сведения о бронировании, пассажире, маршруте, тарифе и посадочном месте |
| `dm.flight_airport_daily` | Дата вылета в UTC и пара аэропортов; число рейсов, отмен, проданных перелетов и их сумма |
| `dm.booking_sales_daily` | Дата бронирования в UTC; число и сумма бронирований, число билетов и оплаченных перелетов |
| `dm.exchange_rates_daily` | Календарная дата и валюта; действующий курс, предыдущее доступное значение и изменение в процентах |

Суммы авиаперевозок выражены в рублях согласно модели источника. Исторические авиаперевозки не пересчитываются по текущим курсам. Число билетов отличается от числа оплаченных перелетов: один билет может включать несколько рейсов. Аналогично сумма бронирования и сумма перелетов являются отдельными показателями и не предполагаются равными без дополнительного бизнес-правила.

### Транзакции и проверки

Полный снимок авиаперевозок в Staging публикуется одной транзакцией Greenplum, обрабатываемый срез ЦБ публикуется отдельной транзакцией. Core и DM обновляются каждый своей общей транзакцией. Предыдущие данные не удаляются отдельным коммитом перед загрузкой. При ошибке выполняется откат данных и технического состояния публикации. Полная замена использует транзакционный TRUNCATE, поэтому читатели могут ждать освобождения блокировки во время обновления. Атомарность между PostgreSQL, MinIO и всей цепочкой DAG не заявляется; идентификатор пакета связывает успешные публикации слоев.

Проверки включают обязательные поля, повторяющиеся основные и альтернативные ключи, диапазоны и перечни значений, ссылки на принятые родительские записи, баланс количества строк с учетом карантина, сверку количества строк и сумм витрин с Core, нормализацию и актуальность курсов. Неизвестная схема или ошибка разбора ответа API останавливает источник, чтобы не заменить рабочие данные пустым набором.

Результаты доступны SQL-запросами:

Полный набор проверочных запросов находится в `sql/edw/003_verify.sql`.

Численные результаты сквозного запуска приведены в [отчете проверки третьего этапа](docs/stage3-verification.md).

```sql
SELECT * FROM dq.pipeline_runs ORDER BY finished_at DESC;
SELECT * FROM dq.layer_state ORDER BY layer;
SELECT * FROM dq.check_results WHERE status <> 'PASS' ORDER BY checked_at DESC;
SELECT batch_id, table_name, reason, count(*)
FROM dq.rejected_records GROUP BY batch_id, table_name, reason;
SELECT * FROM dm.booking_sales_daily ORDER BY booking_date DESC LIMIT 10;
SELECT * FROM dm.exchange_rates_daily ORDER BY request_date DESC, currency_code LIMIT 15;
```

Email-уведомления пока не подключены. Сводка и предупреждения записываются в логи задач Airflow и таблицы DQ. Передача витрин внешнему потребителю не входит в реализацию третьего этапа.

### Тесты

Интеграционные тесты используют отдельную базу с именем, оканчивающимся на `_test`, и откатывают тестовые данные. Создание тестовой базы выполняется один раз:

```powershell
docker compose exec -T greenplum /usr/local/gpdb/bin/createdb -h localhost -U gpadmin edw_stage3_test
docker compose exec -T -e EDW_TEST_DATABASE=edw_stage3_test -e PYTHONPATH=/opt/airflow/plugins airflow-scheduler python /opt/airflow/project-tests/test_edw.py
```

Проверяются точность курсов, различие дат запроса и действия курса, обработка пустого ответа, выбор интервала, карантин и распространение отклонения на зависимые строки, отсутствие умножения сумм бронирований, повторная загрузка и сохранение предыдущих дат, а также откат публикации.

## Статус проекта

Реализованы этапы 1-3: проектирование, инфраструктура, ETL и Data Quality. В Greenplum созданы слои Staging, Core, DM и технические таблицы DQ. Выполнен сквозной запуск на демонстрационной базе авиаперевозок и XML-сервисе ЦБ. Репликация mirror-сегментов и экспериментальное сравнение способов распределения относятся к следующим этапам и пока не выполнены.
